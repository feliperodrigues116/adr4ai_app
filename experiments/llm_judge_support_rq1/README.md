# ADR4AI RQ1: response-conditioned evidence-based support evaluation

This experiment evaluates the evidential support for each **original GPT
classification**, given the unchanged requirement case, five pattern fields,
and that GPT decision's original references and rationale. It is complementary
to the architects' evaluation of the 36 resulting ADRs, which remains the main
empirical evidence. No expert rating is read, reinterpreted, or integrated here.

This is **response-conditioned support evaluation**, not independent blind
classification, a new pattern selection, ground truth, or proof of architectural
correctness. The prior blind Claude experiment and GPT–Claude comparison remain
untouched and do not supply inputs, expected verdicts, or calibration targets.
No comparisons, statistics, or scientific conclusions are generated by this runner.

## Inputs and frozen scope

The original loaders, `build_prompt`, and GPT assessment validator are imported
from `experiments/pattern_selection/prepare_data.py` and `assess_pattern.py`.
The original classification instructions are not modified. Input sources are:

- `data/user_histories_orig.csv`: System Purpose, User Story, Acceptance Criteria,
  with original identifiers and original text, including whitespace/language.
- `catalogs/patterns/P*.json`: only `id`, `name`, `motivation`, `solution`, and
  `consequences` enter the prompt. Other catalog fields are not supplied.
- `experiments/pattern_selection/outputs/assessments.jsonl`: original classification,
  reference array (in its existing order), and rationale, associated by exact
  `(user_story_id, pattern_id)` strings. The GPT model/effort metadata is checked
  for provenance; only the three scientific assessment fields enter the prompt.

There must be exactly 840 unique pairs, the complete 12-story × 70-pattern cross
product, with 36 applicable, 31 not_applicable, and 773 insufficient_information
GPT decisions. Four systems, three stories per system, and 35 acceptance criteria
are validated by the original loader. IDs remain strings, retaining leading zeros.
`source_baseline.json` pins the initial SHA256 inventory of all 74 original source
files (CSV, 70 catalog files, GPT results, and two original Python modules).
Any inventory/hash mismatch fails preflight; the runner never repairs inputs.

The original requirement/pattern prompt is reused byte-for-byte as a prefix,
then a labeled GPT assessment block is appended. The original rationale is
appended directly, not translated, paraphrased, stripped, or normalized. Reference
arrays use JSON encoding, preserving their identifier values and order.

**Excluded from the request and execution inputs:** previous Claude classifications
and rationales, agreement statistics, earlier findings, expert ratings, RAG
results, and generated ADR content. Each call has a fresh, single user message
and no history from any other pair. Preservation tests may hash previous artifacts
solely to verify that they remain unchanged; those bytes never enter a request.

## Fixed neutral evaluation protocol

The exact system instructions are [instructions.txt](instructions.txt), sent
without appended guidance. The complete strict JSON schema is
[response_schema.json](response_schema.json). Both are hashed in the manifest.

### Protocol v1.1: reference and uncertainty clarification

Protocol ID: `adr4ai-rq1-response-conditioned-support-v1.1`.
[protocol_revision.json](protocol_revision.json) records the version, exact added
paragraph, current/previous instruction hashes, and the preserved v1 pilot
manifest hash. The only rubric edit is this paragraph, inserted immediately
before the unchanged support-verdict definitions:

> Protocol clarification: The original GPT protocol requires nonempty requirement_refs only for applicable decisions; empty references are valid for not_applicable and insufficient_information and must not automatically be treated as deficiencies. For insufficient_information, absent architectural details may correctly justify the classification and must not automatically be reported as a deficiency. identified_gaps must contain only concrete, materially relevant limitations in the justification or evidential support of the original GPT decision, not merely details missing from the requirements or permitted omissions of references. Assess whether any such absence actually weakens the justification of the assigned original classification; it neither determines nor favors any support verdict.

Instruction SHA256 (exact UTF-8 file bytes):
`82dd72af7b3d3961ef3ec261d394d92731879e22c3c644f8d4b53af9c07b49f1`.
Instruction SHA256 using the existing manifest's canonical-JSON encoding:
`3600c5d4cbbc7e90fd7a2428b9b5775dc296aac4ee0189beadd64c4c4247997b`.

The v1 pilot's SYS01-US01 × 002 judgment was supported but included empty
original references and missing processing details in its gaps list. Those
outputs remain unchanged. This clarification distinguishes missing information
that justifies an insufficient-information decision from limitations that weaken
its justification; it does not prescribe any verdict, forbid genuinely material
gaps, or change the schema/validator. Regression tests compare the entire rubric
against the original pilot manifest and allow only this one insertion.

The judge assesses the original decision against evidence, with neither agreement
nor disagreement preferred. Architectural alternatives, non-uniqueness, and the
possibility of a different solution do not themselves count against a decision.
Pattern intent matters; unsupported new assumptions and implementation-only
possibilities do not supply missing applicability evidence. System Purpose is
contextual and cannot alone establish applicability. The GPT rationale is neither
assumed correct nor discounted because of its authorship.

Category-specific criteria distinguish positive applicability evidence,
incompatibility/non-applicability evidence, and genuine insufficient information.
Missing positive evidence is not itself non-applicability evidence. Verdicts are:

- `supported`: adequate justification under these criteria, without requiring
  certainty, uniqueness, or the best architecture.
- `partially_supported`: a meaningful evidential basis with a concrete material
  ambiguity/inference/limitation; generic uncertainty or alternatives alone do
  not suffice.
- `unsupported`: inadequate justification or material conflict under the criteria;
  a preference for another pattern alone does not suffice.

The same evidential standards apply across categories and verdicts. No deficiencies
are invented, sought merely to lower the verdict, or overlooked merely to raise it.

## Model, response handling, and validation

Configuration reuses the validated Messages API delivery conventions:

- Fixed model `claude-sonnet-5-5`; no alternate provider/model option or fallback.
- `thinking={"type":"adaptive"}`; `output_config.effort="high"`.
- `output_config.format={"type":"json_schema","schema":...}` with the new
  four-field support schema, not the blind-classification schema.
- `anthropic==1.17.0`; live mode rejects another installed SDK version.
- `--max-tokens` defaults to 32768 (reasoning and answer share the limit).
- `--timeout` defaults to 600 seconds. Both must be finite/positive as applicable.
- API key comes only from `ANTHROPIC_API_KEY`; SDK retries are explicitly zero.
  The official `https://api.anthropic.com` base URL is explicit.

The answer must contain exactly `verdict`, `evidence_refs`, `rationale`, and
`identified_gaps`. Verdict is one of the three support categories; arrays must
contain strings. Every evidence identifier must belong to the evaluated case.
Rationale must be a nonempty explanation (a local semantic-minimum check beyond
the schema's string type, implementing the requirement to explain the verdict).
Empty reference arrays are allowed when appropriate. Empty gap arrays, including
for supported judgments, are accepted. No verdict-dependent minimum gap/reference
count is imposed. Structural checks cannot establish whether a rationale or gap
is substantively justified; that is the task being evaluated.

Accept only `stop_reason=end_turn`, the exact configured response model, and
exactly one text block, optionally accompanied by thinking/redacted-thinking
blocks. Parse only the text block. Duplicate JSON fields, non-finite JSON values,
extra/missing fields, wrong types, foreign references, malformed JSON, refusals,
truncation (even with valid-looking JSON), and unexpected blocks all fail.
There is no extraction from Markdown, output repair, verdict conversion, or
silent retry. Thinking content is neither persisted nor reused in later requests.

Run from the repository root with Python 3.10+ (Linux/Unix flock is used).
Default preflight requires no SDK, key, or network and creates no output files:

```bash

# Equivalent explicit command:
python -B experiments/llm_judge_support_rq1/run_experiment.py --preflight
```

Preflight validates source integrity, counts, coverage, association, every prompt,
the schema, fixed API configuration, reproducibility metadata, output safety, and
any existing manifest/journals. It prints all three pilot IDs. Its default scope
is the official 840-pair plan; it never constructs an API client.

## Persistence, provenance, and protocol freezing

Only this new experiment's `outputs/` tree is writable by the runner:

- Revised pilot: `outputs/claude-sonnet-5-5/v1.1/technical_pilot/`.
- Revised official: `outputs/claude-sonnet-5-5/v1.1/full/`.

Default paths include the protocol version. The original v1 pilot remains in
`outputs/claude-sonnet-5-5/technical_pilot/`; its manifest, results, attempts,
events, and hashes are preserved. Its original instructions remain embedded in
its manifest. Do not resume or merge that pilot with v1.1. Explicitly selecting
its old directory with revised code is rejected by the manifest check.

`--output-dir` can choose a different child directory within that tree. Previous
experiment/report directories, root output paths, symlink entries, and unknown
output inventories are rejected. Pilot/full manifests cannot be interchanged.

Each run stores only its own files:

- `manifest.json`: exclusive creation, immutable protocol/configuration, complete
  source inventory and raw-file hashes, relevant new code/configuration hashes,
  original GPT counts, all-input digest, selected pair IDs, GPT classifications,
  input/prompt hashes, **full prompt text for every planned pair**, complete system
  instructions/schema/API configuration, retry policy, creation timestamp.
- `attempts.jsonl`: fsynced intent before each call, attempt/execution IDs and
  number, pair/GPT classification, manifest/input/prompt hashes, start timestamp.
- `results.jsonl`: fsynced only after strict validation, original GPT classification,
  returned support judgment, raw JSON answer text, validation status, requested/
  actual model, effort/thinking, start/end timestamps, elapsed time, usage,
  response/request IDs, content block types, and original provider metadata.
  Provider metadata excludes content blocks to avoid storing thinking content.
- `events.jsonl`: execution start/completion/failure, Python/platform, coverage
  status, explicit retry decision and pending pairs, error type, available HTTP
  status/request ID/Retry-After, and metadata/text of rejected model responses.

No API key or arbitrary exception text is written. Source-file/code hashes are
checked at planning, before requests, and before final completion. Other hashes
use canonical sorted compact JSON encoded as UTF-8, including logical prompt
strings; raw source files use SHA256 of their exact bytes. Full prompt texts and
source hashes make this distinction auditable. Relevant source hashes identify
code versions without requiring Git tracking or a clean shared working tree.

Repeat the exact command to resume. The runner locks the directory, validates
all saved judgments and their raw JSON, metadata, attempt associations, and
provenance, and skips every validated pair. Duplicate pairs, response IDs, attempt
IDs, or incompatible manifests fail. It never silently overwrites an official run.
Final completion requires re-reading all journals and verifying exact planned
coverage and source integrity. Changes to instructions, schema, code, sources,
model/configuration, or scope reject resumption. **Freeze the protocol before the
official experiment begins; do not edit it in response to results.**

## Failure and retry policy

On an API/validation failure or interruption, stop immediately and keep validated
results. No automatic SDK or application retries occur. Inspect the attempt and
failure metadata; respect any provider Retry-After before an explicit retry.
Append `--retry-unfinished` to the same live command to authorize another attempt
for unfinished pairs. This action is logged. At most three reserved attempts per
pair are allowed, including interrupted or invalid attempts. Validated judgments
are never repeated or selectively replaced based on their verdicts.

A network interruption may follow remote processing/billing; exactly-once remote
execution cannot be guaranteed. Repeating an unfinished attempt may incur another
charge. A truncated journal is rejected with no silent byte removal; manual
inspection is required. Do not discard failed-attempt history to bypass limits.
Failures are not verdicts. No automatic token-budget increase, effort reduction,
model fallback, or prompt change is permitted. A deliberately different protocol
requires separately recorded outputs and an explicit methodological decision;
it must not be blended into a started official run.

## Methodological limitations and deviations

Receiving GPT's classification and rationale can **anchor** the judge. This is
intentional response conditioning, and it limits independence. The same inputs
and a fixed rubric reduce uncontrolled variation but cannot remove model bias,
shared model tendencies, stochastic variability, or the possibility of multiple
legitimate architectural interpretations. The label high is provider-specific;
adaptive thinking need not consume reasoning tokens on every request.

A valid schema/reference ID is not proof of substantive evidential support.
The support judgments are complementary model-based evidence, not human ground
truth or proof that an architecture is correct. Existing architect ratings remain
unchanged and are neither used for calibration nor merged into this protocol.
No blind outcomes, previous findings, agreement statistics, RAG results, or ADR
content are used to calibrate the rubric or target verdict distributions.

There are no scope/model/rubric deviations. Explicit bounded retries and the
nonempty-explanation check are implementation choices documented above. Structural
neutrality tests check input isolation and rubric safeguards, not semantic
impartiality or the eventual distribution/validity of model judgments.
